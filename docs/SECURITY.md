# Security design

**Vantrel Security is pre-release development software and must not be relied upon as the sole antivirus or endpoint protection solution.** It performs no threat detection or protection today.

## Trust boundaries

- The WPF desktop runs as a normal user. It is not granted service-management or administrator rights.
- The installed worker runs as `NT AUTHORITY\LocalService`, a built-in account with minimal local privileges and anonymous network credentials. Its installed files are copied to an Administrator-controlled Program Files directory. It needs read/execute access there, not write access. See [Microsoft's LocalService account description](https://learn.microsoft.com/en-us/windows/win32/services/localservice-account).
- The named pipe crosses from an untrusted interactive user process into the service. All requests are untrusted, even when the Windows ACL permits the connection. Status, System Health, Activity, Scan Capability, and component-inspection requests provide no privileged action.

## Named pipe controls

The server supplies its own protected DACL. Its current Windows account receives full control; the Windows Interactive SID receives `ReadData`, `WriteData`, `ReadAttributes`, `ReadPermissions`, and `Synchronize`. No Everyone, anonymous, or network-logon allow rule is added. These are individual rights: Windows maps generic pipe write to `FILE_CREATE_PIPE_INSTANCE`, which would let clients create server instances, so the client is not granted generic write. See [Microsoft's named-pipe rights documentation](https://learn.microsoft.com/en-us/windows/win32/ipc/named-pipe-security-and-access-rights).

The Interactive SID covers local console and Remote Desktop logons, while network logons do not carry that SID; see [Microsoft's SID descriptions](https://learn.microsoft.com/en-us/windows-hardware/drivers/kernel/sddl-for-device-objects). Remote SMB pipe clients and anonymous logons therefore do not pass this DACL. The client itself uses the local `.` endpoint. The service requests `FirstPipeInstance` and retains the one pipe instance until it stops. If another process already owns the name, pipe startup fails rather than joining that endpoint. The installed desktop accepts a response only while Service Control Manager reports `VantrelSecurityService` as Running. Development bypass is compiled only in Debug builds and additionally requires `DOTNET_ENVIRONMENT=Development`.

The desktop requests `TokenImpersonationLevel.Anonymous`, preventing the server from impersonating its user token through this pipe. This does not make the client anonymous to the DACL; Windows still checks the connecting process token.

## Message handling and logging

Protocol version 1 accepts only the fixed `get_status`, `get_system_health`, parameter-free `get_activity`, parameter-free `get_scan_capability`, and parameter-free `get_component_inspection` types. The service checks the request type and protocol version after a bounded 4 KiB read. The unchanged status response contains service version, heartbeat, and start time. The health response contains a collection timestamp, coarse Windows version/build, elapsed system uptime, system-volume total/free byte counts, and optional Windows Security Center antivirus and firewall category health enums; each unavailable value is null. Activity returns at most 12 fixed typed observations of only those two categories, plus service-start and sampling-through timestamps. Scan Capability is a fixed sampled statement that scanning is not enabled and accepts no target, path, directory, file, filter, schedule, category, exclusion, option, token, or payload. Component inspection likewise accepts no payload and returns only a bounded outcome, reason, sampling time, fixed policy revision, and for an observed result an SHA-256 and byte count. No product name, firewall profile or rule, volume path, label, serial number, user detail, internal file path, file identity, or arbitrary client-selected target crosses the pipe. The service collects and caches samples outside the pipe loop. Both sides use asynchronous operations, cancellation, and timeouts. Unsupported, malformed, and oversized input receives no valid response. No CLR type names, commands, paths, or executable code are accepted over IPC.

Installed-service lifecycle and error logs go to the Windows Application Event Log. The installer registers a dedicated source; Windows bounds the log size through its existing retention settings. Development mode uses console logging. IPC warnings are rate-limited by matching failure and include only a fixed lifecycle stage, reason, exception type, and numeric HRESULT. Connection and completed-response events are each limited to one per minute. The Release desktop shows sanitized SCM, connection, I/O, and protocol failure details in its service-status card, including pipe name and received byte count. Request payloads, secrets, tokens, and personal data are not logged or displayed.

## Known limits

- Any local interactive user can request the same non-sensitive status and coarse machine-health values and can briefly occupy the single pipe instance. No per-user policy or concurrency limit beyond the three-second connection deadline exists yet.
- Windows version/build is informational, not a patch-compliance judgment. System uptime and disk space do not indicate protection state. Sampling failures remain unavailable, and samples over two minutes old are marked stale in the desktop. Task 004 installed LocalService validation passed on 2026-09-18: the non-elevated desktop received real values and a sample timestamp, disconnected when the service stopped, then reconnected to a newer sample in the same process after restart.
- Task 005 introduced [`WscGetSecurityProviderHealth`](https://learn.microsoft.com/en-us/windows/win32/api/wscapi/nf-wscapi-wscgetsecurityproviderhealth) for `WSC_SECURITY_PROVIDER_ANTIVIRUS`. Its result is Windows' aggregate category state, not evidence that Vantrel protects the machine. It accepts only documented states. `S_FALSE` (including its accompanying `POOR` output), other failures, and unexpected values become Unavailable. Matching diagnostics are rate-limited and contain only fixed reasons, HRESULTs, optional numeric state, and exception type. Installed LocalService validation passed on 2026-09-18: the non-elevated desktop displayed Good while Vantrel Protection Status stayed Unavailable, disconnected when the service stopped, then reconnected to a newer Good sample in the same process after restart. Other states and failure paths were verified with injected tests, not by changing Windows Security Center.
- Task 006 reuses the WSC call for only the fixed `WSC_SECURITY_PROVIDER_FIREWALL` category (`0x1`). The adapter has no public provider-argument method and accepts no provider flag from IPC. Its aggregate result does not audit individual firewall profiles or rules. Only `S_OK` with a documented health value is shown; `S_FALSE` with its accompanying `POOR` output, other failures, and unexpected values are Unavailable. A collection failure in either category does not suppress the other result. Installed LocalService validation passed on 2026-09-18: the non-elevated desktop showed Good for both Windows-reported categories, retained Vantrel Protection Status Unavailable, disconnected on service stop, and reconnected to a newer sample in the same process after restart. Other WSC states and failures remain covered by injected tests.
- Task 007 Activity is a memory-only, 12-entry history of observed changes in the two existing Windows-reported categories. Initial observations explicitly have no previous state. Entries are sampled observations, not proof of when a Windows state changed, and are not Vantrel detections, alerts, or protection events. The desktop clears displayed entries on disconnect and marks stale sampling. Any local interactive user who can query the existing pipe can read the same coarse Activity history. Installed LocalService validation passed on 2026-09-18: a non-elevated desktop saw two initial Good observations, cleared them on service stop, then reconnected to a fresh session without previous-session entries. Synthetic state transitions remain covered by automated tests; installed validation did not manipulate Windows Security Center, antivirus, or firewall settings.
- Task 008 Scan Capability is a fixed, read-only, cached statement that Vantrel performs no scanning. The source has no filesystem dependency and does not enumerate, open, hash, or inspect files. The Desktop has no start control, target picker, path field, schedule, exclusion, or drag-and-drop operation. Installed LocalService validation passed on 2026-09-18: the non-elevated desktop displayed the fixed snapshot, changed to Disconnected on service stop, and recovered in the same process to a newer sample after restart. Any future client-triggered scan requires a separate authorization and command channel because every interactive local user can query this pipe and the server intentionally does not impersonate the desktop user.
- Task 009 Component Inspection is a fixed Vantrel observation, not a scan. Only an eligible SCM-hosted installed service derives its own loaded `Vantrel.Security.Service.dll`; development and interactive hosts return `NotInstalledService` without opening a checkout file. The Windows-only collector opens that exact target once with `CreateFileW` and `FILE_FLAG_OPEN_REPARSE_POINT`, rejects a reparse point or nonregular target, derives the final path and metadata from the handle, requires exact containment within `Program Files\Vantrel Security\Service`, hashes through that same handle, and verifies identity, length, and write time after reading. It limits input to 16 MiB, uses a 64 KiB buffer and fixed five-second deadline, handles shutdown cancellation without creating a snapshot, and retains one immutable memory-only result. The SHA-256 is an observed component hash only: no expected/reference hash, clean/safe/trusted/verified conclusion, malware detection, Activity event, quarantine, remediation, persistence, or telemetry upload exists.
- The Task 003 paired build passed installed-service validation on 2026-09-17. The service ran under LocalService; the non-elevated desktop stayed connected, showed the expected status, disconnected when the service stopped, and reconnected after restart. Fresh Event Log entries confirmed accepted clients and consumed responses. The single pipe instance and three-second deadline remain availability limits for local interactive clients.
- The project targets .NET 10 LTS. This machine has SDK 10.0.401 and .NET/Windows Desktop runtimes 10.0.12. Keep target machines patched to the current supported .NET 10 runtime; see [Microsoft's support policy](https://dotnet.microsoft.com/en-us/platform/support/policy) and [DEPLOYMENT.md](DEPLOYMENT.md).
- The binaries and PowerShell scripts are unsigned. Review and sign deployment artifacts before production use. The current scripts refuse an existing installation and do not silently elevate.
- Application Event Log source creation, LocalService logging, fresh pipe startup, client connections, and consumed responses were observed in the installed build. The scripts do not change global Event Log retention settings.
- Future privileged features need explicit operations, caller authorization, audit design, and a fresh threat review. Windows-reported posture, Vantrel observations, Vantrel detections with provenance/evidence, and Vantrel actions with authorization/auditing/retention remain separate concepts. Future detections/actions also need separate severity, privacy, persistence, and retention designs. This read-only status, health, Activity, Scan Capability, and component-observation protocol must not be extended into generic command execution, arbitrary path scanning, or a catch-all event feed.

No scanning, Defender-specific control or product enumeration, firewall configuration or profile/rule enumeration, network monitoring, drivers, kernel components, remediation, or personal information collection is implemented. Security-provider queries are limited to the two fixed, read-only categories described above.

## Task 009 installed LocalService validation

Task 009 installed LocalService validation passed on 2026-09-18 after recovery from an initial production activation defect. The first Task 009 service start failed because Microsoft dependency injection could not activate `ComponentInspectionSource`: its fixed parameterless production constructor was `internal`. The corrective change made only that production constructor `public`; the test-only constructor remains `internal`, and the fixed five-second collection deadline remains non-configurable. A production-equivalent DI activation regression test was added. Corrected automated verification passed with zero warnings or errors: 78 of 78 tests in Debug, 78 of 78 in Release, and 17 focused Task 009 tests.

The guarded recovery replaced only `Vantrel.Security.Service.dll`. The prior `AE354E465DCA7CEB81B0C422AE6DF2173F92BAC81BD5FE32DDF54F4642DCCBD1` Service DLL payload is obsolete. The corrected Service DLL SHA-256 is `1CA909A02D04495091D78F3F08CE00D0FD717F48EF7E0EC39030DABAB5D72BC1`.

The installed service remained `NT AUTHORITY\LocalService`. The matching non-elevated desktop showed Dashboard Connected, Protection Status Unavailable, intact System Health, fresh initial Windows-reported firewall and antivirus Activity observations, and Scan Capability disabled. Component Inspection showed a current observation with SHA-256 `1CA909A02D04495091D78F3F08CE00D0FD717F48EF7E0EC39030DABAB5D72BC1` and observed byte count 40,448. It exposed no path, target picker, Start Scan action, trust verdict, malware verdict, quarantine, or remediation feature. Stopping the service changed the same desktop process to Disconnected. Restarting it recovered the same process with a newer component-observation sample, advancing from 10:03:22 AM to 10:08:49 AM; the observed SHA-256 remained unchanged.
