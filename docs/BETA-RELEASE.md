# Beta release layout foundation

`New-BetaReleaseLayout.ps1` is a build-time, two-phase release-layout tool. It does not install software, control a service, open a private key, contact a signing service, or create an installer. Explicit PE signing, when separately invoked through `ReleaseLayoutTool`, remains a later gated operation.

The beta gate requires the exact SDK in `global.json` and a clean immutable checkout. It rejects tracked, untracked, and ignored checkout content before it restores, builds, or publishes. It runs `dotnet restore --locked-mode` against the committed package lock files; ordinary development restores remain unlocked.

`Prepare` requires a checked-out immutable commit, a Release version, release sequence, canonical UTC publication time, and release-notes file. It validates and records those descriptor inputs before publishing. The descriptor version and full source commit are bound to published Service, Desktop, and OfflineUpdateTool informational/build metadata while preserving the existing numeric assembly and file-version behavior. Deterministic and path-independent source settings apply to release publishing.

`Prepare` publishes raw Service output into temporary release-root staging, projects only the seven canonical Service components into `service`, and publishes framework-dependent `win-x64` Desktop and OfflineUpdateTool outputs into fixed `desktop` and `offline-update-tool` directories below an empty caller-supplied root. It writes a canonical descriptor and copies release notes as `release-notes.md`.

The v1 `Prepare`, `Record`, thirteen-PE signing command, installer authoring, and offline updater remain unchanged. The separate Task 073 Service-only v2 path is selected explicitly with `prepare-v2-service`, `sign-v2-service-pes`, and `record-v2-service`. It does not make a v2 layout eligible for the existing installer or offline updater. The v1 seven-component layout is historical release evidence and must not be used as a dependency-complete Service payload.

`prepare-v2-service` requires a separate clean immutable checkout at an explicit full commit, SDK `10.0.401`, a locked solution restore for `win-x64`, Release `net10.0-windows` framework-dependent publishing, an approved source Service lockfile hash, a protected external output parent, and external release notes. It rejects nonordinary Git index flags and compares every tracked working-tree file with its blob in the exact committed HEAD tree using Git's path-aware text/EOL normalization; configured transformations beyond built-in line-ending conversion are rejected. It checks named NTFS streams on every tracked source file before restore and again after publish. It verifies the actual SDK publish against `.deps.json`, then creates a protected Service inventory containing all deployable runtime dependencies. The three exact Service/Core/Infrastructure PDBs are retained only under a separate protected `diagnostic-symbols` directory, measured separately, and excluded from the signed Service inventory. The SDK's exact root `packages.lock.json` copy is verified against the source lock and classified as build residue. Missing dependencies, unrecorded files, reparse paths, named NTFS streams, unsafe ACLs, and changed source inputs fail closed. Preparation emits a canonical descriptor and release notes, but no signed sidecar or release record.

`sign-v2-service-pes` is a separate explicit command for the four Vantrel-owned Service PEs only: Service.exe, Service.dll, Infrastructure.dll, and Core.dll. It validates the prepared dependency-complete layout and source provenance before SignTool, signs those four paths sequentially with SHA-256 and RFC 3161 timestamping, and requires the configured production WinTrust and exact three-EKU policy afterward. It never signs Microsoft, framework, or NuGet dependency DLLs and never writes a manifest or record.

After the four PE signatures pass, the explicit `sign-v2-service-manifest` and `sign-v2-release-metadata` release-tool commands produce the two offline sidecars in that order. Each requires `--source-root`, the exact `--source-commit`, `--output-root`, and an external `--private-key` path; each uses a separate clean source checkout because locked restore creates ignored intermediates. The v2 ManifestTool signing helper receives only an already approved final Service inventory. The command rechecks source provenance, independent unsigned-publish equivalence, all final Service and diagnostic hashes, protected ACL/ADS/reparse state, and the four production Authenticode results before accessing its purpose-specific protected PKCS#8 key. It writes a protected temporary in the release layout's protected same-volume parent, rereads and verifies its exact bytes and signature under the corresponding immutable public root, then rechecks the retained layout and publishes with a final create-new rename. A failed prepublication check cannot leave a producer-created final-path sidecar; any temporary that resists cleanup stays outside the exact layout and cannot be Record evidence. The command rejects key paths under the source checkout or the selected release-layout parent; operators must keep keys outside every release layout. Private bytes are never a command argument, record field, or release file.

The manifest remains the bounded canonical ASCII/LF `vantrel-trusted-manifest-v2` signed inventory at the layout-root `Vantrel.Security.TrustedManifest` path. The metadata sidecar remains the reviewed `vantrel-release-metadata-v1` format at the layout-root `Vantrel.Security.ReleaseMetadata` path: it signs the SHA-256 of the **full signed manifest file**, including its signature, and binds the same version, sequence, and descriptor publication time. The v1 and v2 Record gates use strict, different manifest parsers, so neither sidecar path creates a v1 fallback. The three signing identities remain separate: Azure Authenticode publisher policy, the offline manifest P-256 root, and the offline metadata P-256 root. The v1 ManifestTool commands remain unchanged. These new commands do not invoke Record, MSI authoring, installation, or offline updates; no real v2 release has been signed by this task.

`record-v2-service` requires a separate clean source-checkout preflight, exact signed v2 manifest and release metadata, the four valid Service Authenticode signatures, an exact Service dependency inventory, and the protected diagnostic-symbol inventory. It independently reproduces the unsigned locked SDK publish from that checkout. Non-PE files and diagnostic symbols must match exactly; each owned PE may differ only in its embedded Authenticode certificate table, PE checksum, and certificate-directory entry, and must still pass native WinTrust and the exact production publisher policy. The comparison is deliberately narrower than a general Authenticode file digest; any other byte change fails closed. It reopens the final layout with retained read handles that deny writes and deletion, checks file and directory identities, final paths, ACLs, alternate data streams, exact entries, and hashes, and retains those handles through canonical v2 record publication. The record binds the descriptor commit, release identity, SDK/target/deployment, source lock hash, exact signed manifest and metadata file hashes, canonical manifest payload hash, final Service file hashes, separate diagnostic-symbol hashes, and only sanitized production-policy categories. Unknown record schemas fail closed; v1 records are never parsed as v2. A record is written only after all post-sign checks pass. Each v2 phase needs its own clean checkout at the same commit because the pinned restore creates ignored build intermediates. The source operator and administrators remain trusted: privileged processes under those identities can still alter a filesystem outside a held-handle interval, so a record is evidence of the bounded approval operation, not permanent filesystem immutability.

Task 076 adds a separate whole-product v2 evidence layer. `project-v2-product --source-root <clean-checkout> --source-commit <full-commit> --service-release-root <completed-v2-Service-layout> --output-root <new-protected-layout>` reproduces the pinned, locked `win-x64` Service, Desktop, and OfflineUpdateTool publishes. It copies the existing completed Service evidence unchanged, then projects only the independently validated Desktop and Tool runtime closures into `desktop/` and `offline-update-tool/`. The Tool-local Service DLL and its dependencies belong to the Tool inventory, not the signed Service manifest. Desktop and Tool PDBs are measured under `diagnostic-symbols/`; the Tool publish's exact copied Service apphost, Service `.deps.json`, Service `.runtimeconfig.json`, and source lockfile are hash-checked against independent source evidence but excluded as build residue. The observed Desktop publish has no root lockfile copy. Any other publish file fails closure validation.

The nine Desktop/Tool Vantrel-owned PEs require separate signing under the existing production policy before `record-v2-product --source-root <clean-checkout> --source-commit <full-commit> --output-root <projected-layout>` can succeed. This task adds no automatic signer. The product gate rechecks the exact `beta-release-record-v2.txt` bytes and Service signed sidecars, Service dependency closure and four PE signatures, independent Desktop/Tool publish equivalence, all nine additional WinTrust and exact-profile results, and the complete protected physical layout before a final create-new `product-release-record-v2.txt` publication. Its canonical ASCII/LF record binds the Service record hash, descriptor identity, source lock hashes, final runtime inventories, signed sidecar hashes, fixed diagnostic and source-residue classifications, and sanitized nine-PE evidence. Only the three runtime inventories and the two signed Service sidecars are classified as potential installer inputs. The Service record, product record, descriptor, notes, PDBs, and build residue remain outside that class. This is release evidence only: InstallerPreflight, WiX, and offline updates remain v1-only until separately reviewed integration.

Task 077 adds installed Service verification for the explicitly selected v2 manifest schema. The Service reads only bounded schema framing to select v1 or v2, then reads the complete v2 manifest once from a retained protected handle; it never retries the other parser after a failure. The v1 path retains its seven-component behavior. The v2 path requires the separate production P-256 manifest and metadata signatures, matching version and sequence, metadata binding to the full signed-manifest bytes, and an exact physical Service tree: every signed runtime file and its directories plus only `Vantrel.Security.TrustedManifest` and `Vantrel.Security.ReleaseMetadata`. PDBs, source locks, records, descriptors, notes, extras, named data streams, and reparse paths are rejected. V2 file, sidecar, and directory stream inventories are read from retained handles and rechecked before success; file and sidecar reads use retained read handles that deny write and delete sharing, with bounded hashing, complete file-index/volume identity and final-path rechecks, and a second tree enumeration. A privileged writer acting outside the observation interval remains outside the claim of permanent immutability; installed ACL assumptions have not been changed or VM-validated here.

Installed provenance can now internally identify an authenticated v2 generation, version, sequence, and full signed-manifest SHA-256 without inventing a source commit from an uninstalled product record. A distinct v2 integrity policy revision lets the existing status response distinguish complete v2 inventory from historical v1 seven-file checks; the existing provenance response shape does not separately expose generation or source-commit evidence. The canonical `vantrel-release-policy-v2` durable format adds generation to sequence and manifest hash at the existing fixed policy-file path. A clean v2 first install may bootstrap this policy only after full installed authentication; any existing v1, v2, malformed, partial, or unknown policy file is never replaced by that path. Historical v1 policy bytes remain in their original format, readable by v1 updater consumers. An authenticated v1 identity may be projected and evaluated as generation V1 in memory, without rewriting the durable policy. Task 077 has no policy-v2 replacement path for historical v1 state. Durable v1-to-v2 migration is deferred to a future coordinated transaction with journal and recovery support; existing v1 offline-update readers safely reject the v2 schema. V1-to-v2 higher-sequence transition requires that coordination; v2-to-v1 ordinary transition is blocked. Existing offline candidate verification, journal, rollback, installer, and MSI paths remain v1-only and cannot consume this runtime capability as update authorization.

Task 078 adds a separate, internal, read-only generation-aware offline verifier for a caller-authorized Service root. A bounded exact manifest header selects v1 or v2 once. V1 uses the unchanged nine-file `OfflineReleaseVerifier` chain; v2 reuses the Task 077 installed verifier's retained-handle, exact-tree, reparse, final-path, file-identity, named-stream, and bounded-hash checks, including the two signed sidecars. Every invocation authenticates the physical root again. The result contains the generation, sequence, full signed-manifest SHA-256 and, for v2, an immutable inventory from the verified manifest; it does not convey source-commit or product-record provenance or authorize a later copy. Policy assessment reads canonical historical v1 or policy-v2 bytes without rewriting them. A higher-sequence v1-to-v2 candidate is reported as requiring coordinated migration, while an ordinary v2-to-v1 transition is blocked. The current Administrator admission, fixed preflight, private-copy, backup, health, transaction, and recovery callers still use the v1-only verifier and exact nine-file contract. No v2 update execution, variable-inventory copying, journal change, rollback change, or durable policy migration is enabled.

Task 079A adds a separate, canonical V2-to-V2 transaction journal, closed phase model, protected store, and identity-based physical-state classification contract. Its fixed journal location is separate from the historical fixed-file V1 journal; a future admission and startup coordinator must treat either malformed journal or simultaneous V1/V2 journals as a conflict and use the same exclusive update-operation owner lock. These types do not copy files, switch Service directories, start or stop the Service, commit policy, or execute recovery. The historical V1 transaction remains unchanged. V1-to-V2 migration and V2 update execution remain unsupported until separately reviewed transaction and recovery integration is complete.

Task 079B adds isolated V2 variable-inventory artifact storage primitives under `Updates\V2Artifacts\Transactions\<transaction-id>\candidate` and `Updates\V2Artifacts\Backups\<backup-id>`, separate from both V1 storage and the V2 journal directory. Each copy freshly authenticates its fixed-role source, copies exactly the signed runtime inventory and two signed sidecars through protected file handles into a create-new tree, then independently authenticates the complete destination and checks its expected V2 identity. A failure after destination creation may leave occupied residue for explicit review; the primitive never merges a retry into that tree or recursively deletes uncertain content. Full artifact retirement is a separate primitive requiring fresh V2 authentication and exact physical-tree checks before handle-bound, nonrecursive deletion. An interrupted retirement can also leave blocking residue; later transaction recovery must define its disposition. Production artifact roots require pre-provisioned Administrator/SYSTEM-only protection; no production update caller invokes these primitives yet. Directory-entry durability, whole-tree power-loss behavior, and protected-ACL creation under the intended elevated operator still need real-Windows validation. The copy result is observation evidence, not transaction authorization: later update phases must reauthenticate the physical artifact. V2 update execution, Program Files switching, Service stop/start, policy commit, rollback/recovery, and V1-to-V2 migration remain unsupported.

Task 079C adds dormant Program Files V2 filesystem primitives. They create a dependency-complete prepared Service sibling from a freshly authenticated private candidate, then expose four separate guarded physical moves: detach the predecessor, activate the prepared target, detach an activated target for rollback, and restore the predecessor. Each move authenticates the expected physical roots before and after one same-parent rename; a failure after the rename attempt requires fresh physical classification and never triggers an automatic compensating move. The prepared-copy result records only an observation, not lasting authorization. The prepared tree has an explicit protected Administrator/SYSTEM full-control and LocalService read/execute ACL, distinct from private ProgramData artifacts. These child descriptors do not prove the effective rights on the Program Files product parent: before any production caller is connected, provisioning and coordination must constrain and validate that LocalService cannot create or delete canonical or managed siblings through parent rights. No exact product-parent ACL is defined by Task 079C. The privileged update operator and other processes with that identity remain inside the trusted-operator boundary; retained handles do not isolate those peers. The two forward moves and the two rollback moves are not atomic pairs. No production V2 transaction caller, journal advancement, Service stop/start, policy commit, startup recovery, or V1-to-V2 migration is connected. Before a future production detach or rollback-detach call, a coordinator must prove SCM STOPPED and persist durable journal intent. NTFS on the reviewed Windows Home target is the current filesystem scope; ReFS file-ID portability, directory-entry durability after sudden power loss, and elevated ACL/move validation remain separate gates. Task 079B and 079C observations do not authorize later update steps without fresh authentication.

Task 079D adds a dormant, internal pre-stop coordinator for only `Admitted`, `PrivateReady`, and `BackupReady`. Every invocation requires the already-held historical offline-update ownership lease for the exact Updates root, freshly checks both V1 and V2 durable journals, and reads (never commits) the durable V2 policy. Admission authenticates the installed predecessor and fixed staged V2 target before creating an exact-absence journal. Each later invocation prepares at most one Task 079B ProgramData artifact and performs at most one exact-current phase transition. After an interrupted copy, an exact private candidate or predecessor backup can be freshly reauthenticated and reconciled; invalid, partial, foreign, or unavailable residue blocks advancement and is never recursively cleaned. A durable `PrivateReady` or `BackupReady` phase requires its artifacts to remain freshly valid. These observations are not lasting authorization for later update steps. There is no public V2 update entry point and no connection to the historical V1 administrator or OfflineUpdateTool. Historical V1 admission is not yet V2-aware after the owner lease is released; a reviewed cross-generation conflict gate for both admissions is mandatory before V2 admission becomes production reachable. This coordinator does not prepare a Program Files target, call SCM, stop or start the Service, write a recovery nonce, commit policy, retire artifacts, or reach `TargetReady`. The Task 079C Program Files product-parent ACL gate remains mandatory before later integration; V2 updating is not yet enabled.

Task 079E1A defines two dormant security foundations. A single fixed cross-generation lock under `Updates` has a protected Administrators/SYSTEM-only descriptor and a retained lease; LocalService needs no mutation access to it. The lock is not yet provisioned or wired into V1 or V2 admission or terminal retirement, and the separate generation journal locks remain. Task 079E1B must reconcile historical V1 Updates-root ACL application with the exact shared-lock parent ACL before provisioning the lock or wiring V1 and V2 admissions and terminal retirements through the elevated owner lease and this shared lock. Each new admission must retain both leases across both journal observations and its generation-specific absent-to-present publication. Task 079E1A also defines and validates an exact protected descriptor for the Program Files `Vantrel Security` product parent. Administrators/SYSTEM full-control and Users read/execute ACEs inherit to new children so Desktop and OfflineUpdateTool remain readable; LocalService read/execute applies to the parent only, and the Service child retains its independent protected descriptor without inheriting Users rights. Neither LocalService nor Users has parent mutation or delete-child rights. This task does not provision or repair that directory. A new clean V2 MSI must establish the parent contract, and later execution must validate it; the historical signed V1 candidate is unchanged. No V2 Program Files preparation or switching, SCM operation, startup admission, policy commit, or state-model revision is connected by these foundations.

The current ManifestTool `sign` and `sign-release-metadata` commands remain v1-only. Their fixed seven-component payload checks cannot approve a dependency-complete v2 Service. The v2 sidecar producer is explicitly composed in ReleaseLayoutTool so it can reuse the Task 073 filesystem and source gates without a project-reference cycle; its canonical signing helper lives in ManifestTool. A real v2 candidate still requires a separately approved signing operation and successful `record-v2-service` gate. Installer and offline-update integration remain unsupported.

After `Prepare`, the explicitly invoked release-tool signing command signs only the documented Vantrel-owned PE allowlist using external Azure Artifact Signing infrastructure and ignored local metadata. The repository contains no certificate, private key, thumbprint, or token. The four signed Vantrel Service PE files are then covered by the existing trusted manifest with the descriptor release version; separately signed release metadata follows with the same display version.

`sign-authenticode-layout --output-root <prepared-layout-root> --signtool <explicit-x64-signtool.exe> --dlib <explicit-Azure.CodeSigning.Dlib.dll> --metadata <ignored-local-metadata.json>` is the only production composition root for PE signing. It accepts only a prepared, unrecorded layout, signs the exact thirteen Vantrel-owned PEs in canonical order with SHA-256 and RFC 3161 timestamping, then runs the configured `vantrel-production` Authenticode gate. It uses no wildcard or directory signing and never writes a release record. The checked-in metadata template and ignored local file contain only fixed public endpoint/account/profile values and an optional fixed interactive-browser-only `ExcludeCredentials` set; no arbitrary credential chain configuration is accepted.

The required order is `Prepare`, explicit PE signing, external trusted-manifest signing, external release-metadata signing, then `Record`. PE signing alone is not a completed release.

Task 072 provisions two separate fresh public roots for the trusted manifest and release metadata without changing either signed format or key identifier. The corresponding private PKCS#8 keys remain outside Git and every release layout; encrypted offline backup is still pending. This is a fresh start with no fallback to the former roots. Layouts prepared before offline public-root provisioning must be discarded as release candidates and freshly prepared from the provisioning commit. Record verifies the signed sidecars and payload hashes; it does not independently establish which offline trust roots are embedded in the Service binaries.

`inspect-authenticode --file <explicit-pe-path>` is a manual, read-only validation aid for one local PE. It applies ordinary Windows Authenticode validation and the fixed Vantrel Artifact Signing EKU requirements, then emits only sanitized categories. It neither approves a release nor writes a record, and it does not configure the production signing profile.

`Record` requires the non-secret signing-profile alias and verifies Authenticode before the existing public custom-signature checks. Following controlled real-signing validation of Windows trust, RFC 3161 timestamping, and the exact EKUs, the source-owned `vantrel-production` profile is provisioned with an immutable Azure Artifact Signing policy. It requires exactly the code-signing EKU, Azure Artifact Signing Public Trust EKU, and the durable Vantrel certificate-profile EKU; it rejects generic Azure markers, other profile EKUs, and subject or issuer-name similarity. A rotating leaf certificate SHA-256 is audit evidence only and is never the production trust anchor. The gate also requires exactly one approved primary embedded signature, SHA-256 file digest, and a valid supported RFC 3161 timestamp under normal online whole-chain revocation behavior. `Record` then confirms manifest release and metadata display version, hashes every distributable file, and writes only relative safe verification evidence. It writes no partial record on failure.

Reproducible build inputs establish what was built; later external Authenticode signing and existing manifest/metadata signing establish separate signature evidence. This tool verifies but does not create Authenticode signatures.

A completed release layout can be passed to the build-only InstallerPreflight tool with an explicit Windows Installer numeric product version. It verifies the canonical release record, every recorded file and hash in the final layout, and the exact nine-file Service payload before selecting installer inputs. Recorded direct-child `.pdb` files and exact `packages.lock.json` residue in Desktop or OfflineUpdateTool are validated but omitted from the MSI plan; unrecorded, missing, redirected, or other ineligible files fail validation. The plan is not an MSI and cannot install, repair, upgrade, downgrade, uninstall, start a service, create ProgramData, or coordinate an offline update transaction.

The WiX Toolset v7 first-install authoring project consumes only that validated plan. It creates a per-machine x64 MSI model for the fixed Program Files Service, Desktop, and OfflineUpdateTool payloads; registers the LocalService demand-start service without starting it; registers the Application Event Log message resource; and adds one non-advertised all-users Start-menu shortcut. It excludes ProgramData and all update, policy, journal, backup, staging, private-candidate, and lock roots. The MSI has no custom actions and does not implement repair, upgrade, downgrade, rollback coordination, or uninstall coordination. It is not a signed or distributable beta installer.

The read-only `inspect-msi-authenticode --file <explicit-msi-path>` command opens a Windows Installer database and extracts signature evidence from the retained file handle and open WinTrust provider state. It does not approve a release or write a record. A controlled disposable MSI signing run established that the native MSI evidence reader and the restricted-staging handle transition work with the approved signer; it did not create a distributable MSI. The explicit `sign-msi-distribution` command is the only production MSI signing entry point. It requires `--output-root`, `--installer-plan`, `--unsigned-msi`, `--unsigned-msi-sha256`, `--signed-msi`, `--distribution-record`, `--signtool`, `--dlib`, and `--metadata`. The supplied unsigned hash must have been approved separately. It requires a completed validated layout, its exact canonical plan, absent staging and record outputs, and canonical interactive-browser-only local metadata. Builds, Prepare, Record, and tests do not invoke this command.

The command calls the same one-copy foundation: it copies from a retained source handle into create-new staging restricted by ACL to the operator, Administrators, and SYSTEM, captures the unsigned compound-storage inventory while a read handle denies writes and replacement, releases only the incompatible leaf handle for one signing attempt, then reacquires a write-denying read handle. It checks file and parent identity, paths, reparse status, and ACLs before comparing the complete inventory and requiring native WinTrust success, one primary signature, SHA-256 digest, valid RFC 3161 timestamp, the exact production three-EKU policy, and stable final bytes. The comparison permits only the two root signature streams, their deterministic red-black-tree insertion into existing directory slots, necessary root metadata and signature-owned allocations. Original streams, metadata, and padding remain unchanged. Directory, FAT, MiniFAT, DIFAT, and header capacity changes fail closed; another legitimate signer allocation pattern needs separate review. Stream names alone never establish cryptographic acceptance. The parent handle is an identity check, not a rename barrier. Staging trusts the operator and cannot isolate other processes running as that operator during signing.

Only after all checks pass, the command writes a create-new canonical distribution record outside the layout and staging directory. That record contains only the relative MSI filename, final MSI SHA-256, validated release-record and installer-plan SHA-256 values, policy ID, and sanitized verification categories. A failed signer, comparison, native check, input check, or publication leaves no accepted record. A completed signed candidate still requires isolated installation validation and separate distribution approval. This command never installs or runs an MSI.

`Prepare-WindowsSandboxValidation.ps1` is a host-side preparation harness. It requires a clean detached checkout at the exact source commit, matching release metadata, a completed release record, and a canonical installer plan. It may build and hash the unsigned MSI, then prepares read-only Sandbox input and a public validation manifest; it never installs an MSI or controls a service. A completed record remains unavailable until separately approved publisher-policy provisioning and external signing are complete.

The signed-candidate workflow is separate. Build `Vantrel.Security.InstallerPreflight` in Release with the pinned SDK and locked restore, then invoke `scripts/Prepare-SignedWindowsSandboxValidation.ps1` with `-ReleaseLayoutRoot`, `-InstallerPlanPath`, `-SignedMsiPath`, `-DistributionRecordPath`, `-SignedMsiSha256`, `-InstallerPlanSha256`, `-ReleaseRecordSha256`, `-DistributionRecordSha256`, and a new absolute `-SandboxOutputRoot` outside the checkout and layout. The script uses the already built tool with `--no-build --no-restore`; it never invokes WiX or signs or installs the MSI. The tool fully revalidates the completed layout and canonical plan, parses the canonical distribution record, checks all four separately approved hashes and bindings, and copies the existing signed MSI from a retained file handle. It rechecks the copy and emits the distinct `vantrel-signed-sandbox-input-v1.txt` format. The script adds the fixed signed-candidate validator and generates an XML-escaped `.wsb` configuration with the approved distribution-record hash supplied outside the mapped input. Inside Sandbox, the private MSI copy is held open for reading with write and delete sharing denied through installation, then its identity, path, and bytes are checked again. A sharing incompatibility fails closed. An existing output path is rejected. Review the generated input and configuration before separately approving launch; preparing them is not installation approval. Compatibility with a real Windows Sandbox MSI installation remains untested.

From the reviewed tooling checkout, the preparation commands are:

```powershell
dotnet restore .\tools\Vantrel.Security.InstallerPreflight\Vantrel.Security.InstallerPreflight.csproj --locked-mode
dotnet build .\tools\Vantrel.Security.InstallerPreflight\Vantrel.Security.InstallerPreflight.csproj --configuration Release --no-restore
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\Prepare-SignedWindowsSandboxValidation.ps1 `
  -ReleaseLayoutRoot '<completed-layout>' -InstallerPlanPath '<canonical-plan>' `
  -SignedMsiPath '<existing-signed-msi>' -DistributionRecordPath '<canonical-distribution-record>' `
  -SignedMsiSha256 '<approved-uppercase-sha256>' -InstallerPlanSha256 '<approved-uppercase-sha256>' `
  -ReleaseRecordSha256 '<approved-uppercase-sha256>' -DistributionRecordSha256 '<approved-uppercase-sha256>' `
  -SandboxOutputRoot '<new-absolute-external-directory>'
```

On a supported host, open the generated `Vantrel.Security.SignedReleaseValidation.wsb` only after that separate approval. Its single read-only mapping points to `C:\VantrelInput`; networking, clipboard, printer redirection, and vGPU are disabled. Before installation, the signed-candidate validator independently parses its canonical plan, manifest, and distribution record, compares the distribution record with the separately approved hash carried by the `.wsb` command, rehashes the signed MSI, plan, and completed release record, and checks every cross-binding. It rejects extra, missing, or redirected mapped inputs. The older unsigned `vantrel-sandbox-input-v1.txt` format and validator remain separate.

Windows Sandbox requires a supported Windows Pro, Enterprise, or Education edition (Home is unsupported), AMD64 for this `win-x64` MSI, enabled hardware virtualization or nested virtualization, and the [documented minimum resources](https://learn.microsoft.com/en-us/windows/security/application-security/application-isolation/windows-sandbox/windows-sandbox-install). The Sandbox feature must be enabled on that host. The isolated installation check does not launch the Desktop, start or exercise the service or IPC, test Event Log rendering, verify the shortcut target, or test repair, upgrade, uninstall, or offline-update recovery; those remain separate future validation work.

Windows Sandbox is the only Task 064 installation location. Its configuration disables networking, clipboard, printer redirection, and vGPU, and maps only the prepared input directory read-only. The sandbox-only validator verifies the MSI and plan hashes, fixed installed-file hashes, the stopped LocalService demand-start service, Event Log message resource, the one Start-menu shortcut, absence of a desktop shortcut, and absence of Vantrel ProgramData update and policy roots. It does not launch the Desktop, start the service, repair, uninstall, or run an offline update.

Existing development management scripts remain separate and are not beta installer tooling.
